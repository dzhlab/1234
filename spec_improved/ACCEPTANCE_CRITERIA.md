## Введение

Этот документ содержит **детальные критерии приемки (Acceptance Criteria)** для всех функциональных требований системы RG System. Каждый критерий описывает конкретное, проверяемое условие, которое должно быть выполнено для успешного завершения функции.

### Назначение

- ✅ Обеспечить единое понимание требований между всеми участниками проекта
- ✅ Предоставить QA инженерам четкие критерии для тестирования
- ✅ Помочь разработчикам понять границы и условия каждой функции
- ✅ Упростить процесс code review и приемки функций

## Управление соревнованиями

### 1.1. Создание нового соревнования

**User Story:** Как организатор, я хочу создать новое соревнование, чтобы начать регистрацию участников и судей.

**Priority:** High

#### Acceptance Criteria:

- **AC-1.1.1:** Форма создания соревнования содержит все обязательные поля
  - **Given:** Организатор авторизован и находится на странице создания соревнования
  - **When:** Форма отображается
  - **Then:** Видны все обязательные поля: название (RU), название (EN), дата начала, дата окончания, место проведения, тип соревнования, уровень соревнования
  - **Verification:** Визуальная проверка формы, все поля помечены красной звёздочкой (*)

- **AC-1.1.2:** Валидация: дата окончания >= дата начала
  - **Given:** Форма создания соревнования открыта
  - **When:** Пользователь вводит дату окончания раньше даты начала
  - **Then:** Отображается ошибка валидации "Дата окончания не может быть раньше даты начала"
  - **Verification:** Кнопка "Создать" неактивна, сообщение об ошибке красного цвета под полем

- **AC-1.1.3:** Валидация: название не пустое и не превышает 200 символов
  - **Given:** Форма создания соревнования открыта
  - **When:** Пользователь оставляет поле названия пустым или вводит >200 символов
  - **Then:** Отображается соответствующая ошибка: "Обязательное поле" или "Максимум 200 символов"
  - **Verification:** Проверка с пустым полем и строкой в 201 символ

- **AC-1.1.4:** Автоматическая генерация дней соревнования
  - **Given:** Дата начала = 2025-03-01, дата окончания = 2025-03-03
  - **When:** Организатор создаёт соревнование
  - **Then:** Система автоматически создаёт 3 дня соревнования с датами 01.03, 02.03, 03.03
  - **Verification:** Проверка в БД таблицы `competition_days`, должно быть 3 записи

- **AC-1.1.5:** Присвоение уникального ID соревнованию
  - **Given:** Форма заполнена корректно
  - **When:** Пользователь нажимает "Создать соревнование"
  - **Then:** Система генерирует UUID и присваивает его соревнованию
  - **Verification:** Проверка формата ID: должен быть валидный UUID v4 (regex: `^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`)

- **AC-1.1.6:** Установка статуса "Подготовка" по умолчанию
  - **Given:** Соревнование создаётся
  - **When:** Запись сохраняется в БД
  - **Then:** Поле `status` = 'preparation'
  - **Verification:** SELECT status FROM competitions WHERE id = [новый_id]

- **AC-1.1.7:** Успешное перенаправление после создания
  - **Given:** Соревнование успешно создано
  - **When:** Запись сохранена в БД
  - **Then:** Пользователь перенаправляется на страницу соревнования `/competitions/{id}`
  - **Verification:** Проверка URL в адресной строке браузера

- **AC-1.1.8:** Отображение уведомления об успехе
  - **Given:** Соревнование успешно создано
  - **When:** Происходит перенаправление
  - **Then:** Отображается зелёное уведомление "Соревнование успешно создано"
  - **Verification:** Проверка наличия toast-уведомления с классом `success`

### 1.2. Редактирование соревнования

**User Story:** Как организатор, я хочу редактировать соревнование, чтобы исправить ошибки или обновить информацию.

**Priority:** High

#### Acceptance Criteria:

- **AC-1.2.1:** Доступ к редактированию только для организатора
  - **Given:** Пользователь с ролью "Judge" пытается открыть страницу редактирования
  - **When:** GET запрос на `/competitions/{id}/edit`
  - **Then:** Возвращается 403 Forbidden
  - **Verification:** HTTP status code = 403

- **AC-1.2.2:** Форма предзаполнена текущими данными
  - **Given:** Организатор открывает страницу редактирования соревнования
  - **When:** Страница загружается
  - **Then:** Все поля формы заполнены текущими значениями из БД
  - **Verification:** Сравнение значений в форме с данными из БД

- **AC-1.2.3:** Невозможность изменить дату начала если соревнование началось
  - **Given:** Соревнование имеет статус "in_progress" или "completed"
  - **When:** Организатор пытается изменить дату начала
  - **Then:** Поле "Дата начала" заблокировано (disabled)
  - **Verification:** Проверка атрибута `disabled` на input поле

- **AC-1.2.4:** Валидация при сохранении изменений
  - **Given:** Организатор изменяет данные в форме
  - **When:** Нажимает "Сохранить"
  - **Then:** Применяются те же правила валидации, что и при создании
  - **Verification:** Проверка всех критериев из AC-1.1.2, AC-1.1.3

- **AC-1.2.5:** История изменений записывается
  - **Given:** Организатор изменяет название соревнования
  - **When:** Сохраняет изменения
  - **Then:** В таблице `audit_log` создаётся запись с действием 'competition_updated'
  - **Verification:** SELECT * FROM audit_log WHERE entity_id = {competition_id} ORDER BY created_at DESC LIMIT 1

### 1.3. Удаление соревнования

**User Story:** Как организатор, я хочу удалить ошибочно созданное соревнование.

**Priority:** Medium

#### Acceptance Criteria:

- **AC-1.3.1:** Невозможность удалить соревнование с участниками
  - **Given:** Соревнование имеет зарегистрированных участников (count > 0)
  - **When:** Организатор пытается удалить соревнование
  - **Then:** Отображается ошибка "Невозможно удалить соревнование с зарегистрированными участниками"
  - **Verification:** HTTP 400, код ошибки RG-COMP-BUSINESS-001

- **AC-1.3.2:** Подтверждение перед удалением
  - **Given:** Организатор нажимает кнопку "Удалить соревнование"
  - **When:** Нет зарегистрированных участников
  - **Then:** Отображается модальное окно с подтверждением "Вы уверены, что хотите удалить это соревнование?"
  - **Verification:** Модальное окно с кнопками "Да, удалить" и "Отмена"

- **AC-1.3.3:** Мягкое удаление (soft delete)
  - **Given:** Пользователь подтверждает удаление
  - **When:** Выполняется операция удаления
  - **Then:** Запись в БД помечается как удалённая (deleted_at = текущее время), но физически не удаляется
  - **Verification:** SELECT deleted_at FROM competitions WHERE id = {id}, значение NOT NULL

- **AC-1.3.4:** Соревнование исчезает из списка
  - **Given:** Соревнование помечено как удалённое
  - **When:** Организатор просматривает список соревнований
  - **Then:** Удалённое соревнование не отображается в списке
  - **Verification:** Запрос GET /api/competitions не включает удалённые записи

## Регистрация участников

### 2.1. Индивидуальная регистрация спортсмена

**User Story:** Как организатор, я хочу зарегистрировать спортсмена, чтобы он мог участвовать в соревновании.

**Priority:** High

#### Acceptance Criteria:

- **AC-2.1.1:** Форма регистрации содержит все обязательные поля
  - **Given:** Организатор открывает форму регистрации спортсмена
  - **When:** Форма отображается
  - **Then:** Видны поля: ФИО, дата рождения, регион, клуб, тренер, программы (обручи, мяч и т.д.)
  - **Verification:** Проверка наличия всех полей в DOM

- **AC-2.1.2:** Валидация: возраст соответствует категории
  - **Given:** Категория "Юниоры" (13-15 лет), текущий год 2025
  - **When:** Организатор вводит дату рождения 01.01.2000 (25 лет)
  - **Then:** Отображается ошибка "Возраст не соответствует категории"
  - **Verification:** Сообщение об ошибке, кнопка "Сохранить" неактивна

- **AC-2.1.3:** Автоматический расчёт возраста
  - **Given:** Дата рождения = 15.03.2010, текущий год = 2025
  - **When:** Пользователь выбирает дату рождения
  - **Then:** Система автоматически вычисляет и отображает возраст = 14 (или 15)
  - **Verification:** Поле "Возраст" заполняется автоматически

- **AC-2.1.4:** Выбор предметов (apparatus)
  - **Given:** Спортсмен участвует в программе с булавами и лентой
  - **When:** Организатор выбирает эти предметы в чекбоксах
  - **Then:** В БД сохраняются связи в таблице `athlete_apparatus`
  - **Verification:** SELECT apparatus_id FROM athlete_apparatus WHERE athlete_id = {id}, должно быть 2 записи

- **AC-2.1.5:** Генерация стартового номера
  - **Given:** В соревновании уже 10 спортсменов
  - **When:** Регистрируется 11-й спортсмен
  - **Then:** Ему присваивается стартовый номер 11
  - **Verification:** SELECT start_number FROM athletes WHERE id = {new_id}, значение = 11

- **AC-2.1.6:** Проверка дубликатов
  - **Given:** Спортсмен с таким же ФИО и датой рождения уже зарегистрирован
  - **When:** Организатор пытается зарегистрировать дубликат
  - **Then:** Отображается предупреждение "Возможно, этот спортсмен уже зарегистрирован"
  - **Verification:** HTTP 409 Conflict, код RG-ATHLETE-BUSINESS-001

### 2.2. Массовая регистрация через Excel

**User Story:** Как организатор, я хочу загрузить список спортсменов из Excel, чтобы быстро зарегистрировать всех участников.

**Priority:** High

#### Acceptance Criteria:

- **AC-2.2.1:** Поддержка форматов .xlsx и .xls
  - **Given:** Организатор выбирает файл для загрузки
  - **When:** Формат файла = .xlsx или .xls
  - **Then:** Файл принимается для обработки
  - **Verification:** Проверка MIME type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet

- **AC-2.2.2:** Отклонение файлов других форматов
  - **Given:** Организатор пытается загрузить .csv или .txt
  - **When:** Отправляет файл
  - **Then:** Возвращается ошибка "Неподдерживаемый формат файла. Используйте .xlsx или .xls"
  - **Verification:** HTTP 400, код RG-UPLOAD-VALIDATION-001

- **AC-2.2.3:** Шаблон Excel доступен для скачивания
  - **Given:** Организатор на странице массовой регистрации
  - **When:** Нажимает "Скачать шаблон"
  - **Then:** Скачивается файл template.xlsx с заголовками столбцов и примером
  - **Verification:** Проверка содержимого файла: заголовки ФИО, Дата рождения, Регион, Клуб и т.д.

- **AC-2.2.4:** Валидация структуры файла
  - **Given:** Загружен файл без обязательных столбцов
  - **When:** Система обрабатывает файл
  - **Then:** Возвращается ошибка со списком недостающих столбцов
  - **Verification:** Сообщение "Отсутствуют столбцы: [список]"

- **AC-2.2.5:** Предпросмотр перед импортом
  - **Given:** Файл успешно загружен и прошёл валидацию
  - **When:** Обработка завершена
  - **Then:** Отображается таблица с данными из файла для подтверждения
  - **Verification:** Таблица содержит все строки из файла с возможностью редактирования

- **AC-2.2.6:** Пропуск строк с ошибками
  - **Given:** Файл содержит 100 строк, 5 из них с ошибками валидации
  - **When:** Организатор выбирает "Импортировать валидные записи"
  - **Then:** Импортируется 95 записей, 5 с ошибками пропускаются и выводится отчёт
  - **Verification:** COUNT(*) FROM athletes = 95, отчёт со списком ошибочных строк

- **AC-2.2.7:** Ограничение размера файла
  - **Given:** Размер файла > 5 МБ
  - **When:** Организатор пытается загрузить файл
  - **Then:** Отображается ошибка "Размер файла превышает 5 МБ"
  - **Verification:** HTTP 413 Payload Too Large

### 2.3. Редактирование данных спортсмена

**User Story:** Как организатор, я хочу редактировать данные спортсмена, чтобы исправить ошибки.

**Priority:** Medium

#### Acceptance Criteria:

- **AC-2.3.1:** Невозможность изменить ФИО после начала выступлений
  - **Given:** Спортсмен уже выступил (есть оценки)
  - **When:** Организатор пытается изменить ФИО
  - **Then:** Поле ФИО заблокировано (disabled)
  - **Verification:** Атрибут disabled на input поле

- **AC-2.3.2:** Возможность изменить стартовый номер до начала выступлений
  - **Given:** Спортсмен ещё не выступал
  - **When:** Организатор меняет стартовый номер с 5 на 10
  - **Then:** Изменения сохраняются, старый номер 5 становится доступным
  - **Verification:** UPDATE athletes SET start_number = 10; проверка уникальности

- **AC-2.3.3:** История изменений сохраняется
  - **Given:** Изменены данные спортсмена
  - **When:** Сохранение выполнено
  - **Then:** В audit_log записывается старое и новое значение
  - **Verification:** JSON diff в поле `changes`

## Судейство

### 3.1. Выставление D-score (сложность)

**User Story:** Как судья D-бригады, я хочу выставить оценку за сложность программы.

**Priority:** High

#### Acceptance Criteria:

- **AC-3.1.1:** Панель содержит поля для всех компонентов D-score
  - **Given:** Судья открывает панель D-score
  - **When:** Интерфейс загружается
  - **Then:** Видны поля: DB (телесные элементы), DA (элементы с предметом), DS (танцевальные шаги), DD (динамические элементы с бросками)
  - **Verification:** 4 input поля типа number с шагом 0.1

- **AC-3.1.2:** Валидация: DB >= 0 и DB <= 10
  - **Given:** Судья вводит значение DB
  - **When:** Значение < 0 или > 10
  - **Then:** Отображается ошибка "Значение должно быть от 0 до 10"
  - **Verification:** Проверка с -1 и 11

- **AC-3.1.3:** Автоматический расчёт итогового D-score
  - **Given:** DB = 3.5, DA = 2.4, DS = 0.4, DD = 1.8
  - **When:** Судья вводит все значения
  - **Then:** Система автоматически вычисляет D = 3.5 + 2.4 + 0.4 + 1.8 = 8.1
  - **Verification:** Поле "Итого D-score" отображает 8.1

- **AC-3.1.4:** Округление до 0.1
  - **Given:** Судья вводит DB = 3.567
  - **When:** Фокус уходит с поля
  - **Then:** Значение автоматически округляется до 3.6
  - **Verification:** Значение в поле = 3.6

- **AC-3.1.5:** Сохранение происходит только при заполнении всех полей
  - **Given:** Заполнены только DB и DA
  - **When:** Судья пытается сохранить
  - **Then:** Кнопка "Сохранить" неактивна или отображается ошибка
  - **Verification:** Кнопка disabled до заполнения всех 4 полей

- **AC-3.1.6:** Отображение таймера выступления
  - **Given:** Выступление началось
  - **When:** Секретарь запустил таймер
  - **Then:** Судья видит обратный отсчёт времени (90 сек → 0)
  - **Verification:** WebSocket событие `performance_timer_started` обновляет UI

- **AC-3.1.7:** Невозможность изменить оценку после подтверждения
  - **Given:** Судья сохранил и подтвердил D-score
  - **When:** Пытается изменить значение
  - **Then:** Все поля заблокированы, отображается сообщение "Оценка подтверждена"
  - **Verification:** Атрибут readonly на всех input

### 3.2. Выставление E-score (исполнение)

**User Story:** Как судья E-бригады, я хочу выставить оценку за исполнение программы.

**Priority:** High

#### Acceptance Criteria:

- **AC-3.2.1:** Начальное значение E-score = 10.0
  - **Given:** Судья открывает панель E-score
  - **When:** Интерфейс загружается
  - **Then:** Отображается начальное значение 10.0
  - **Verification:** Поле "Базовая оценка" = 10.0

- **AC-3.2.2:** Система сбавок с предопределёнными значениями
  - **Given:** Судья хочет применить сбавку
  - **When:** Открывает список сбавок
  - **Then:** Видит кнопки: -0.1, -0.3, -0.5, -1.0
  - **Verification:** 4 кнопки с соответствующими значениями

- **AC-3.2.3:** Автоматический расчёт итогового E-score
  - **Given:** Базовая оценка 10.0, применены сбавки -0.3, -0.5, -0.1
  - **When:** Судья нажимает на кнопки сбавок
  - **Then:** Система вычисляет E = 10.0 - 0.3 - 0.5 - 0.1 = 9.1
  - **Verification:** Поле "Итого E-score" = 9.1

- **AC-3.2.4:** Отмена последней сбавки
  - **Given:** Судья ошибочно применил сбавку -0.5
  - **When:** Нажимает кнопку "Отменить"
  - **Then:** Последняя сбавка удаляется из списка, E-score пересчитывается
  - **Verification:** Массив сбавок уменьшается на 1 элемент

- **AC-3.2.6:** Минимальное значение E-score = 0

## Расчёт результатов

### 4.1. Расчёт итоговой оценки

**User Story:** Система автоматически рассчитывает итоговую оценку по формуле FIG.

**Priority:** High

#### Acceptance Criteria:

- **AC-4.1.1:** Применение формулы: Final = D + E + A - ND - Penalties
  - **Given:** D = 8.1, E = 9.1, A = 8.5, ND = 0.3, Penalties = 0.0
  - **When:** Система рассчитывает итоговый балл
  - **Then:** Final = 8.1 + 9.1 + 8.5 - 0.3 - 0.0 = 25.4
  - **Verification:** SELECT final_score FROM performances WHERE id = {id}, значение = 25.4

- **AC-4.1.2:** Расчёт E-score с исключением крайних значений
  - **Given:** E-судьи выставили: 9.1, 9.3, 9.2, 8.9, 9.0
  - **When:** Система рассчитывает итоговый E-score
  - **Then:** Исключаются max (9.3) и min (8.9), среднее = (9.1 + 9.2 + 9.0) / 3 = 9.1
  - **Verification:** Вычисление в функции calculateEScore()

- **AC-4.1.3:** Округление до 0.001
  - **Given:** Final = 25.4567
  - **When:** Результат сохраняется
  - **Then:** Значение округляется до 25.457
  - **Verification:** DECIMAL(5, 3) в БД

- **AC-4.1.4:** Автоматический пересчёт при изменении компонентов
  - **Given:** D-score изменился с 8.1 на 8.3
  - **When:** Обновление сохранено
  - **Then:** Система автоматически пересчитывает Final = 8.3 + 9.1 + 8.5 - 0.3 = 25.6
  - **Verification:** Trigger в БД или service layer автоматически вызывает recalculate()

- **AC-4.1.5:** Логирование всех расчётов
  - **Given:** Выполнен расчёт итоговой оценки
  - **When:** Final сохранён
  - **Then:** В таблице calculations_log записываются все компоненты и формула
  - **Verification:** JSON: {d: 8.1, e: 9.1, a: 8.5, nd: 0.3, penalties: 0, final: 25.4}

### 4.2. Обработка ничьих (Tiebreak)

**User Story:** Система автоматически разрешает ситуации с одинаковыми итоговыми оценками.

**Priority:** Medium

#### Acceptance Criteria:

- **AC-4.2.1:** Приоритет: E-score
  - **Given:** Спортсмен А: Final=25.4 (D=8.1, E=9.3), Спортсмен Б: Final=25.4 (D=8.3, E=9.1)
  - **When:** Система применяет правило tiebreak
  - **Then:** Спортсмен А занимает более высокое место (E=9.3 > E=9.1)
  - **Verification:** rank_a < rank_b

- **AC-4.2.2:** Если E равны, приоритет D-score
  - **Given:** А: Final=25.4 (D=8.1, E=9.3), Б: Final=25.4 (D=8.3, E=9.3)
  - **When:** E-scores равны
  - **Then:** Спортсмен Б занимает более высокое место (D=8.3 > D=8.1)
  - **Verification:** rank_b < rank_a

- **AC-4.2.3:** Если D и E равны, приоритет A-score (для групп)
  - **Given:** Группа А и Б имеют равные Final, D, E
  - **When:** Сравнивается A-score
  - **Then:** Группа с большим A получает лучшее место
  - **Verification:** Логика в функции resolveTie()

- **AC-4.2.4:** Если все оценки равны, присваиваются одинаковые места (ex aequo)
  - **Given:** Все компоненты абсолютно равны
  - **When:** Невозможно определить победителя
  - **Then:** Обоим спортсменам присваивается одинаковое место, следующее место пропускается
  - **Verification:** Rank = 1, 1, 3 (не 1, 1, 2)

### 4.3. Формирование рейтинга

**User Story:** Система автоматически формирует рейтинг участников по категориям и предметам.

**Priority:** High

#### Acceptance Criteria:

- **AC-4.3.1:** Сортировка по убыванию итогового балла
  - **Given:** 5 спортсменов с баллами: 25.4, 24.1, 26.0, 23.5, 25.4
  - **When:** Система формирует рейтинг
  - **Then:** Порядок: 26.0 (1), 25.4 (2), 25.4 (2), 24.1 (4), 23.5 (5)
  - **Verification:** SELECT * FROM rankings ORDER BY final_score DESC

- **AC-4.3.2:** Разделение по категориям

  - **Then:** Создаётся отдельный рейтинг для каждой категории
  - **Verification:** Две таблицы рейтинга: category_id = 'juniors', category_id = 'adults'

- **AC-4.3.3:** Разделение по предметам
  - **Given:** Спортсмен выступал с мячом и обручем
  - **When:** Формируется рейтинг
  - **Then:** Создаётся рейтинг по мячу и отдельный по обручу
  - **Verification:** Две записи в rankings с apparatus_id = 'ball' и 'hoop'

- **AC-4.3.4:** Многоборье (All-Around)
  - **Given:** Спортсмен выступал с 4 предметами
  - **When:** Рассчитывается многоборье
  - **Then:** Итоговый балл = сумма баллов по всем 4 предметам
  - **Verification:** all_around_score = SUM(final_score) GROUP BY athlete_id

- **AC-4.3.5:** Обновление в реальном времени
  - **Given:** Добавлена новая оценка
  - **When:** Расчёт выполнен
  - **Then:** Рейтинг обновляется автоматически, всем пользователям отправляется WebSocket событие
  - **Verification:** WebSocket 'rankings_updated' с новыми данными

  - **When:** Отправляет первое сообщение {type: 'auth', token: 'jwt...'}
  - **Then:** Сервер проверяет токен и возвращает {type: 'auth_success'}
  - **Verification:** Без auth токена соединение закрывается через 5 секунд

- **AC-8.2.3:** Подписка на события соревнования
  - **Given:** Клиент авторизован
  - **When:** Отправляет {type: 'subscribe', competition_id: '123'}
  - **Then:** Сервер добавляет клиента в комнату 'competition:123'
  - **Verification:** Клиент получает только события этого соревнования

- **AC-8.2.4:** Событие 'score_updated' при изменении оценки
  - **Given:** Судья сохраняет D-score = 8.1
  - **When:** Оценка сохраняется в БД
  - **Then:** Всем подписанным клиентам отправляется {type: 'score_updated', performance_id, score}
  - **Verification:** Проверка получения события в браузере

- **AC-8.2.5:** Reconnection при разрыве соединения
  - **Given:** WebSocket соединение прервалось
  - **When:** Клиент обнаруживает разрыв
  - **Then:** Автоматически переподключается с exponential backoff: 1s, 2s, 4s, 8s...
  - **Verification:** Логирование попыток переподключения

- **AC-8.2.6:** Heartbeat для поддержания соединения
  - **Given:** WebSocket соединение установлено
  - **When:** Прошло 30 секунд без активности
  - **Then:** Клиент отправляет ping, сервер отвечает pong
  - **Verification:** Соединение не закрывается при долгом бездействии

## Производительность

### 9.1. Время отклика API

**User Story:** Система быстро обрабатывает запросы пользователей.

**Priority:** High

#### Acceptance Criteria:

- **AC-9.1.1:** GET запросы выполняются за < 200ms (p95)
  - **Given:** Нагрузка 50 одновременных пользователей
  - **When:** Выполняются GET /api/competitions
  - **Then:** 95% запросов завершаются менее чем за 200ms
  - **Verification:** Prometheus метрика http_request_duration_ms_bucket

- **AC-9.1.2:** POST запросы выполняются за < 500ms (p95)
  - **Given:** Создание нового спортсмена
  - **When:** POST /api/athletes
  - **Then:** 95% запросов завершаются менее чем за 500ms
  - **Verification:** Нагрузочное тестирование с k6 или Artillery

- **AC-9.1.3:** Запросы к БД оптимизированы (использование индексов)
  - **Given:** Запрос списка спортсменов с фильтром по региону
  - **When:** Выполняется SELECT * FROM athletes WHERE region = 'Moscow'
  - **Then:** EXPLAIN показывает использование индекса idx_athletes_region
  - **Verification:** EXPLAIN ANALYZE в PostgreSQL

- **AC-9.1.4:** Кэширование часто запрашиваемых данных в Redis
  - **Given:** Список соревнований запрашивается часто
  - **When:** Выполняется GET /api/competitions
  - **Then:** Результат кэшируется в Redis на 5 минут, последующие запросы берутся из кэша
  - **Verification:** Проверка Redis: GET competitions:list

### 9.2. Масштабируемость

**User Story:** Система поддерживает одновременную работу 500 пользователей.

**Priority:** Medium

#### Acceptance Criteria:

- **AC-9.2.1:** Поддержка 500 одновременных WebSocket соединений
  - **Given:** Нагрузочный тест с 500 клиентами
  - **When:** Все подключаются к WebSocket
  - **Then:** Все соединения успешно установлены, latency < 1s
  - **Verification:** Нагрузочное тестирование с Artillery ws-plugin

- **AC-9.2.2:** Горизонтальное масштабирование API серверов
  - **Given:** 2 инстанса API сервера за Nginx load balancer
  - **When:** Запросы распределяются round-robin
  - **Then:** Каждый инстанс обрабатывает ~50% запросов
  - **Verification:** Логи Nginx, проверка распределения

- **AC-9.2.3:** Session stickiness для WebSocket
  - **Given:** Клиент подключён к WebSocket на сервере A
  - **When:** Отправляет последующие сообщения
  - **Then:** Все сообщения маршрутизируются на сервер A (sticky session)
  - **Verification:** Настройка Nginx: ip_hash или cookie-based routing

- **AC-9.2.4:** Redis Pub/Sub для синхронизации между серверами
  - **Given:** Событие 'score_updated' на сервере A
  - **When:** Нужно уведомить клиентов на сервере B
  - **Then:** Сервер A публикует в Redis канал, сервер B подписан и получает событие
  - **Verification:** Проверка Redis PUBLISH/SUBSCRIBE

## Безопасность

### 10.1. Защита от SQL Injection

**User Story:** Система защищена от атак типа SQL Injection.

**Priority:** High

#### Acceptance Criteria:

- **AC-10.1.1:** Использование параметризованных запросов
  - **Given:** Запрос SELECT * FROM athletes WHERE name = ?
  - **When:** Параметр name = "'; DROP TABLE athletes; --"
  - **Then:** Значение экранируется, запрос безопасен
  - **Verification:** Code review, проверка использования ORM или prepared statements

- **AC-10.1.2:** Валидация всех пользовательских вводов
  - **Given:** API endpoint принимает ID спортсмена
  - **When:** Передан параметр id = "1 OR 1=1"
  - **Then:** Валидация отклоняет значение как невалидный UUID
  - **Verification:** Regex проверка формата UUID перед запросом к БД

- **AC-10.1.3:** ORM (Object-Relational Mapping) защищает от инъекций
  - **Given:** Использование Sequelize или TypeORM
  - **When:** Запрос через ORM: Athletes.findOne({where: {name: userInput}})
  - **Then:** ORM автоматически экранирует параметры
  - **Verification:** Проверка генерируемых SQL запросов в логах

### 10.2. Защита от XSS (Cross-Site Scripting)

**User Story:** Система защищена от атак типа XSS.

**Priority:** High

#### Acceptance Criteria:

- **AC-10.2.1:** Экранирование HTML в пользовательском контенте
  - **Given:** Имя спортсмена = "<script>alert('XSS')</script>"
  - **When:** Отображается на странице
  - **Then:** Выводится как текст: &lt;script&gt;alert('XSS')&lt;/script&gt;
  - **Verification:** Проверка HTML-кода страницы

- **AC-10.2.2:** Content Security Policy (CSP) заголовок
  - **Given:** Приложение загружается в браузере
  - **When:** Проверяются HTTP заголовки
  - **Then:** Присутствует Content-Security-Policy: default-src 'self'; script-src 'self'
  - **Verification:** DevTools → Network → Headers

- **AC-10.2.3:** Использование React/Vue автоматически экранирует вывод
  - **Given:** React компонент: <div>{userName}</div>
  - **When:** userName содержит <script>
  - **Then:** React автоматически экранирует, скрипт не выполняется
  - **Verification:** Проверка в DOM, наличие экранированных символов

### 10.3. HTTPS и защита данных в transit

**User Story:** Все данные передаются по защищённому каналу.

**Priority:** High

#### Acceptance Criteria:

- **AC-10.3.1:** Все HTTP запросы перенаправляются на HTTPS
  - **Given:** Пользователь открывает http://rgsystem.local
  - **When:** Запрос обрабатывается сервером
  - **Then:** Происходит редирект 301 на https://rgsystem.local
  - **Verification:** HTTP status code = 301, Location header

- **AC-10.3.2:** TLS 1.2 или выше
  - **Given:** Клиент устанавливает HTTPS соединение
  - **When:** Проверяется версия TLS
  - **Then:** Используется TLS 1.2 или TLS 1.3
  - **Verification:** OpenSSL: openssl s_client -connect domain:443 -tls1_2

- **AC-10.3.3:** Действующий SSL сертификат
  - **Given:** Проверка сертификата
  - **When:** Клиент подключается
  - **Then:** Сертификат валиден, не истёк, выпущен доверенным CA
  - **Verification:** Браузер не показывает предупреждений о безопасности

### 10.4. Защита паролей

**User Story:** Пароли пользователей надёжно защищены.

**Priority:** High

#### Acceptance Criteria:

- **AC-10.4.1:** Хеширование паролей с bcrypt
  - **Given:** Пользователь регистрируется с паролем "SecurePass123!"
  - **When:** Пароль сохраняется в БД
  - **Then:** Сохраняется bcrypt хеш, cost factor = 12
  - **Verification:** SELECT password FROM users, проверка формата: $2b$12$...

- **AC-10.4.2:** Пароль не передаётся в логах или ответах API
  - **Given:** Запрос GET /api/users/me
  - **When:** Возвращаются данные пользователя
  - **Then:** Поле password отсутствует в ответе
  - **Verification:** Response JSON не содержит поле password

- **AC-10.4.3:** Требования к сложности пароля
  - **Given:** Пользователь создаёт пароль
  - **When:** Вводит "123456"
  - **Then:** Отображается ошибка "Пароль должен содержать минимум 8 символов, заглавные и строчные буквы, цифры"
  - **Verification:** Валидация с regex: ^(?=.*[a-z])(?=.*[A-Z])(?=.*\d).{8,}$
